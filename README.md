# 麦麦营养求解器 mcd-nutrition-optimizer

> 你说「我想吃得清淡点」，它算出麦当劳 158 款餐品里最适合的那一餐。

**🎬 [打开演示页 →](docs/demo.html)** （浏览器直接打开，无需 Token）

**只读工具，不下单不领券不改账户。相同输入永远得到相同输出，每个数字都能复现。**

## 它解决什么问题

你说「想吃得清淡点」，但你不知道清淡是多少毫克钠。
你也不会说「我要 500 大卡」，你只会说「别太撑」。

本Skill 做的是**把口语偏好翻译成数值约束，再用官方真实数据算出答案**：

```
你：想吃得清淡点
 ↓翻译
钠 ≤ 500mg、热量 ≤ 600kcal
 ↓ 求解
冰美式小杯 + 可乐大杯 + 纯牛奶（盒装）
363kcal · 蛋白 8g · 钠 73mg
```

### 1. 配置 MCP

复制 `mcp-config.example.json` 为你的 `mcp.json`，把 `<在此填入你的MCP_TOKEN>`
换成从 [open.mcd.cn/mcp](https://open.mcd.cn/mcp) 申请的 Token：

```json
{
  "mcd-mcp": {
    "type": "streamablehttp",
    "url": "https://mcp.mcd.cn",
    "headers": {
      "Authorization": "Bearer <在此填入你的MCP_TOKEN>"
    }
  }
}
```

### 2. 安装 Skill

把本目录放进你的 skills 目录（WorkBuddy 为 `~/.workbuddy/skills/`），重启客户端即可。

### 3. 用起来

直接说人话，不需要记命令：

- 想吃得清淡点
- 500 大卡以内的午餐
- 高蛋白，钠别超 200mg
- 巨无霸三件套一共多少大卡

**先试 [`docs/demo.html`](docs/demo.html)** —— 不需要 Token，浏览器打开就能看到求解结果、套餐账本和覆盖率报告。

## 数据从哪来：全部实测，不估算

这个项目的每个数字都能复现。`tests/fixtures/` 下有 5 份从
`https://mcp.mcd.cn` 真实抓取的数据：

```bash
python scripts/smoke_test.py
```

会逐条验证本文档里的数字。跑不过就是有问题。

| 抓取内容 | 实测量 |
|---|---|
| 官方营养表全量 | 160 条（158 唯一） |
| 门店菜单 | 128 个餐品 |
| 套餐选配轮次 | 3 个套餐 |
| 门店距离与营业时段 | 5 家门店 |
| 活动日历 | 10 个活动 |

**为什么不查公开资料**：官方营养表是静态快照，门店菜单是实时数据，
两者对不上。实测某门店菜单 128 个餐品里，**只有 27 个能在营养表里找到
（21.1%）**——龙焰鸡腿堡、厚薯泥培根肉酱双牛堡、马苏里拉拉丝芝士条等
新品全部未收录。

所以本项目的立场是：**命中就算命中，命不中就说没有，不用估算值代替。**

## 这个项目和其他营养类项目有什么不同

市面上的营养类工具，多数给你一个答案。我们给你答案 **加上它凭什么可信**。

**1. 活动新品的营养收录率是 0%**

实测活动日历推的 7 种餐品，营养表一条都没收录：

```
龙焰鸡腿堡 / 龙焰芝士棒鸡腿堡 / 马苏里拉拉丝芝士条
蓝莓爆爆珠麦旋风 / 灰焰圆筒 / 蘸酱炸鸡 / 鸡薯双全盒
```

**活动日历每天在推的新品，恰好是营养表覆盖不到的那批。**
你看到活动推荐时，很可能算不出它的营养值——这是数据源的时间差，
我们如实告诉你，不会给你一个编出来的数字。

**2. 缺数据就说缺，不填 0**

官方营养表有 4 条记录的热量与蛋白质同时为 0（无糖可口可乐中/大/小杯、
纯悦）。这不是零热量食物，是**官方营养表没有收录它们**。

判据是「热量与蛋白质同时为 0」，不是「四个字段全为 0」——实测无糖可乐的
碳水字段是 1 而非 0，用全零判据会让它被当成真实数据，然后以
「0 大卡 2mg 钠」的身份成为最优解。这是开发中实际踩到的 bug。

遇到套餐子项缺数据时，我们**拒绝输出部分和**：

| 套餐 | 热量 | 状态 |
|---|---|---|
| 巨无霸三件套 | 949 kcal | 完整 |
| 酥酥多笋卷四件套 | 948 kcal | 完整 |
| 人气经典随心配 | — | 缺「可乐麦炫酷」，**拒绝输出** |

**3. 「营业中」这个词我们不信接口**

`businessStatus: true` 只表示门店存在。实测凌晨 2 点时三家门店该字段
全为 `true`，但营业时段都是 06:00-22:00，实际全部未营业。

我们用营业时段做时间比较。直接信那个字段，你会白跑一趟。

**4. 规格歧义不静默取第一个**

菜单的「可乐」对应营养表的中杯/大杯/小杯三条，钠含量不同。工具会列出
全部候选让你选杯型，而不是随便挑一个报给你。

**5. 不迎合你**

要求「钠 ≤ 300mg 的午餐」时，蛋白质 ≥5g 的餐品里钠最低的是优品豆浆
（32mg），再往下全是饮品和奶品，汉堡类钠普遍 500-1000mg。**麦当劳
没有低钠正餐**，我们会这么告诉你。

**6. 儿童场景用儿童阈值，且不给你错误的推荐**

用户告知孩子年龄时按 3-6 / 7-12 / 13-17 岁分段求解。实测不加类别过滤时，
4 岁场景会算出「可乐大杯 + 纯牛奶」——数字全对，但不是儿童餐。这类
「数学最优但荒谬」的组合我们专门写过滤规则挡住了。

同时会主动报告缺口：实测 **17% 餐品钠超学龄前上限 800mg**。

## 三个被修掉的真实 bug

都是实测数据暴露的，不是测试假设出来的：

**Bug 1 · 零值判定** —— 无糖可乐差点以「0 大卡 2mg 钠」成为最优解。

**Bug 2 · 排序策略** —— 纯钠优先使「清淡午餐」收敛到
「冰美式 + 可乐 + 纯牛奶」三样饮品。根因是低钠食物集中在奶品类，
而正餐类钠普遍 500-1000mg。改为「正餐优先 → 钠升序 → 热量升序」。

**Bug 3 · 类别判定顺序** —— 关键词表里「纯牛奶」含"牛"、
「热浓浓抹茶牛奶」含"蛋"（浓**蛋**绿），都先命中了"蛋白"类，
导致「可乐 + 纯牛奶」通过了「必须含主食或蛋白」的校验。
**给 4 岁孩子推荐了汽水加牛奶。** 成人场景下这个 bug 只导致荒谬，
儿童场景下是严重不当。

## 已知限制

**官方营养表对门店菜单的覆盖率有限。** 实测某门店菜单 128 个餐品中，
只有 27 个能在营养表里找到（**21.1%**）。这个数字可用下面的命令自己验证：

```bash
python scripts/coverage_report.py
```

工具会输出分层覆盖率、规格歧义清单和套餐拆解完整性：

```
【匹配层级】
  精确同名21 个   16.4%
  + 剥规格后缀     5 个   20.3%
  + 括号归一化     1 个   21.1%

完全无营养数据  101 个
```

根因是**官方营养表滞后于菜单**，龙焰鸡腿堡、双层脆鸡堡、
厚薯泥培根肉酱双牛堡、马苏里拉拉丝芝士条、韩式烟熏芝士系列等新品
均未收录。归一化只多救回 1 个条目，收益极低。

>一个口径说明：`100%苹果汁(盒装)`（菜单）与 `100%苹果汁`（营养表）
> 只差"(盒装)"这个包装描述。本项目**不剥离括号内容**，
> 因为包装差异可能对应不同配方。只有全角括号与 `【】` 类装饰符会被归一化，
> 因此口径比"激进匹配"少命中 1 个餐品。

另外，菜单里的「可乐」对应营养表的中杯/大杯/小杯三条，钠含量不同。
工具会把这类列为**规格歧义**并列出全部候选，不静默取第一个：

```
【规格歧义：这些餐品对应多个营养表条目】
  可乐
    -> 可乐中杯, 可乐大杯, 可乐小杯
```

所以本项目**只对营养表已收录的餐品做推荐**，不承诺覆盖全部菜单。
遇到未收录餐品如实说明，不估算、不猜测。

**麦当劳没有低钠正餐。** 蛋白质 ≥5g 的餐品里钠最低的是优品豆浆（32mg），
再往下全是饮品和奶品，汉堡类钠普遍在 500-1000mg。要求「低钠午餐」
时本 Skill 会如实告知，而不是硬凑一个没有意义的答案。

其他限制：

- 只支持单品与套餐默认搭配。换套餐选配项后覆盖率会下降
  （实测三件套 77%、四件套 55%、随心配 53%）
- 不支持历史订单热量复盘。`order-list` 不返回任何营养字段，
  且营养表无编码，两者无法可靠关联

## 项目结构

```
docs/
  demo.html                演示页，单文件内联无需依赖
scripts/
  parse_nutrition.py     TOON 格式解析（官方返回非标准 JSON）
  nutrition_solver.py    多目标求解器，正餐优先 + 钠升序
  combo_resolver.py      套餐拆解与子项营养匹配
  child_nutrition.py     儿童按年龄分段求解 + 缺口报告
  store_availability.py  门店营业时段判断
  coupon_scope.py        券适用范围与营养可算性检查
  campaign_gap.py        活动新品与营养表交叉分析
  order_gateway.py       下单安全网关，默认 dry-run
  coverage_report.py     门店营养覆盖率体检
  smoke_test.py          对实测夹具跑基线，验证可复现
  test_solver.py         单元测试
  test_child_nutrition.py  儿童模块测试
  test_store_and_campaign.py  门店/券/活动模块测试
tests/fixtures/          5 份 MCP 实测抓取数据
references/data-notes.md 全部实测踩坑记录
```

## 使用的 MCP 工具

七个，全部只读：

| 工具 | 用途 |
|---|---|
| `list-nutrition-foods` | 唯一主数据源，160 条营养数据 |
| `query-meal-detail` | 套餐拆解取子项 |
| `calculate-price` | 下单前价格预演（可选） |
| `query-nearby-stores` | 门店定位与营业状态 |
| `query-store-coupons` | 券的适用范围检查 |
| `available-coupons` | 可领取的麦麦省券 |
| `campaign-calendar` | 活动日历与新品 |

**不调用** `create-order`、`cancel-order`、`mall-create-order`、
`draw-lottery`、`auto-bind-coupons`、`delivery-create-address`、
`party-order-create` 这 7 个会改动账户或产生消费的工具。

下单能力由 `order_gateway.py` 提供，默认关闭。开发与测试全程未真实执行过
下单，全部走 dry-run 分支。
