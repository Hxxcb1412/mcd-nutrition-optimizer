# 数据实测记录

本文件记录开发过程中对麦当劳 MCP Server 的实测结论。所有数字来自
真实调用 `https://mcp.mcd.cn`，不是文档转述——官方 API 文档页
（open.mcd.cn/mcp/doc）是前端渲染的，抓不到正文。

抓取时间：2026-10-09
测试门店：`1950526`（麦当劳北京新东安二号餐厅）

## 一、list-nutrition-foods 的返回格式

**入参**：无。调用一次返回全量。

**返回不是 JSON**，而是 TOON（Token-Oriented Object Notation）紧凑格式，
官方说明是为了降低 LLM token 消耗：

```
[160]{productName,nutritionDescription,energyKj,energyKcal,protein,fat,carbohydrate,sodium,calcium}:
  猪柳麦满分,null,1288,308,16,16,24,781,213
  ...
```

解析要点：

1. 首行是表头，方括号内是记录数，花括号内是字段名
2. 之后每行一条记录，逗号分隔
3. `null` 需转成 None
4. `nutritionDescription` 几乎全为 null，少数是类比占位文本
   （如纯悦→"能量约清水1杯"、芝士安格斯厚牛堡→"能量约鲈鱼1条"），
   **这些是占位符不是真实营养值**

**单位**：字段本身不带单位声明。按麦当劳中国营养标示惯例为——
energyKj=kJ、energyKcal=kcal、protein/fat/carbohydrate=g、
sodium/calcium=mg。钠的量级（781）与蛋白质（16）差一个数量级，
这个差异佐证了钠是 mg 而非 g。

## 二、数据缺失：4 条零值记录

实测 `energyKcal === 0` 的条目：

- 无糖可口可乐中杯
- 无糖可口可乐大杯
- 无糖可口可乐小杯
- 纯悦

**这些不是零热量食物，是官方营养表未收录它们。**

判定判据是**热量与蛋白质同时为 0**，不是"四个字段全为 0"。
原因：无糖可乐的原始数据是 `0,0,0,0,1,2,0`，
碳水字段是 1 而非 0（见 `tests/fixtures/nutrition.json`）。
若用"四字段全零"作判据，它会被误判成真实数据，
然后以"0 大卡 2mg 钠"的身份成为求解器的最优解——这是开发过程中
实际踩到的 bug。

## 四、营养表与门店菜单的重合度

**营养表没有编码字段**（只有 productName），而门店菜单有编码。
两个数据源只能靠名称匹配，实测重合度见下表（由 `scripts/coverage_report.py` 产出）。

### 归一化必须双侧同时变换

名称归一化要**菜单名和营养表名都过同一函数**才有意义。单侧归一化无新增——
这是容易踩的坑。

本项目的最终口径：

| 层级 | 命中 | 比率 |
|---|---|---|
| 精确同名 | 21/128 | 16.4% |
| + 剥规格后缀 | 5个（累计 26） | 20.3% |
| + 括号归一化 | 1 个（累计 27） | **21.1%** |
| 完全无数据 | 101/128 | 78.9% |

**口径说明**：`100% 苹果汁(盒装)`（菜单）与 `100%苹果汁`（营养表）只差
"(盒装)"这个包装描述。本项目不剥离括号内容——包装差异可能对应不同配方，
静默合并会给出错误营养值。因此口径比"激进匹配"少命中 1 个餐品。

这个取舍是刻意的：宁可少报一个匹配，也不能把不确定的映射说成确定的事实。

实测 `code=4810`：

- `query-meals` 里叫「薯条」
- `query-meal-detail` 里叫「中薯条」
- 营养表里只有「中薯条」，没有「薯条」

即名称不是稳定的关联键，同源名称都不保证一致。

### 根本原因：营养表滞后于菜单

未命中的 100 个条目绝大多数属于这一类，不是命名规则问题。
官方营养表未收录的部分新品，例如：

- 龙焰鸡腿堡
- 双层脆鸡堡
- 厚薯泥培根肉酱双牛堡
- 马苏里拉拉丝芝士条
- 韩式烟熏芝士风味酱系列

**这是本 Skill 只对营养表已收录餐品做推荐的原因**，
也是README「已知限制」一节的依据。

## 五、套餐拆解：query-meal-detail

**入参**：`storeCode`、`orderType`、`beType`、`code`

**返回核心是 `rounds[]` 选配轮次**，每个 choice 含：
code、name、quantity、isDefault、diffPrice。

实测三个真实套餐的子项命中率：

| 套餐 | 默认子项命中 | 全部 choices 命中 |
|---|---|---|
| 巨无霸三件套 (9900005466) | 3/3 | 24/31 (77%) |
| 巨无霸四件套 (9900000888) | 4/4 | 27/49 (55%) |
| 人气超值四件套随心选 (9900004236) | 4/4 | 28/53 (53%) |

**默认搭配100% 命中，全部可选项大幅下降。**

未命中的 54 项集中在：麦咖啡全系（冰/热美式、奶铁、鲜萃冰咖）、
【美汁源】多汁柠柠、纯牛奶、韩式烟熏芝士风味酱系列、
马苏里拉拉丝芝士条、龙焰/脆鸡新堡。

结论：套餐拆解主路径成立，但换选配项后覆盖率会掉。
`diffPrice` 是相对默认项的差价，字符串带 ¥ 且有正负号。

## 六、其他工具的实测坑（未在本 Skill 使用，记录备查）

### 单位不一致

- `query-meals` 的 `currentPrice` 单位是**元**（字符串，如 `"26.5"`）
- `calculate-price` 的价格字段单位是**分**（整数，如 `5050`）
- 但 `calculate-price` 的 `enjoyed.realDiscount` 单位又是**元**

混用会错 100 倍。

### businessStatus 不可信

`query-nearby-stores` 返回的 `businessStatus: true` **只表示门店存在，
不代表当前在营业时间内**。判断"现在能不能买"必须用
`businessStartTime` / `businessEndTime` 配合 `now-time-info` 做时间比较。

### query-my-account 全字段是字符串

包括积分数值（`availablePoint: "0"`）。做算术前必须转数字，
否则会静默字符串拼接。

积分过期字段确实存在：`currentMouthExpirePoint`、`lastMouthExpirePoint`、
`nextMouthExpirePoint`、`expiredPoint`。

### query-meals 的 frequent 字段不存在

官方文档声称有 `frequent`，实际响应中不存在。

### 分类名内嵌换行符

`categories[].name` 含 `\n`，如 `"巨无霸\n牛鱼肉堡"`、`"500\n大卡套餐"`。
字符串比较前必须处理。

### 券必须先定门店

`query-store-coupons` 必填 `storeCode` + `orderType` + `beType`，
不能全局查询券。

### auto-bind-coupons 是不可逆账户变更

入参为空，一次领全部可领券。虽然免费，但领了就占了额度，
且官方未公开每日限领规则。会污染后续 `query-store-coupons` 的输出，
使决策结果不可复现。

## 七、协议与限流

- 接入地址 `https://mcp.mcd.cn`（官方已从旧路径 `/mcp-servers/mcd-mcp` 缩短）
- Streamable HTTP，`Authorization: Bearer <token>`
- 限流：每 Token 每分钟 600 次，超限返回 429
- 401：Token 无效、过期或未提供
- 多个第三方来源交叉验证：**仅支持 MCP Version 2025-06-18 及之前**。
  官方现行 README 已删除该表述，但无证据表明已放宽，建议按此上限配置客户端。
